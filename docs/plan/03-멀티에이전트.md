# 03. 멀티에이전트 구성 (deepagents)

> 상위: [PLAN.md](../PLAN.md) · 시퀀스: [diagrams/publish-cycle-sequence.mermaid](../diagrams/publish-cycle-sequence.mermaid), [diagrams/learning-loop-sequence.mermaid](../diagrams/learning-loop-sequence.mermaid)

## 1. 왜 멀티에이전트인가 — 채택 근거와 반증선

본 루프의 6단계는 상당 부분 순차적이며, "단순 함수 파이프라인 + LLM 호출 몇 개"로도 성립할 수 있다. deepagents 멀티에이전트를 택하는 이유는 **(a)** 사이클 계획·서브에이전트 위임을 Orchestrator가 동적으로 조정(실패 채널 격리·재시도·조건부 스킵)하는 제어 흐름이 정적 파이프라인보다 자연스럽고, **(b)** 각 서브에이전트를 툴 계약 seam으로 독립 개발/교체할 수 있기 때문이다. 다만 본 설계는 의도적으로 LLM을 **착지점 3곳**으로 가두므로, 여기서 "멀티에이전트"는 *자율 재량*이 아니라 *책임 분할 + 오케스트레이션*을 뜻한다.

> **반증선(Phase 0 게이트 연동):** deepagents가 3대 계약(주입·결정론·착지점 통제)을 지원하지 못하거나, 오케스트레이션 이득이 순차 파이프라인 대비 관측되지 않으면 → **자작 오케스트레이터 또는 순수 파이프라인으로 폴백**한다([13](13-로드맵-리스크.md) Phase 0 ①). 즉 멀티에이전트는 *목적이 아니라 검증 대상인 수단*이다.

**[신설 v3] 실용 동기 — 자동화 확장성.** deepagents를 택하는 현실적 이유는 채널·포맷을 늘릴 때(예: 릴스→쇼츠→후속 텍스트 채널) **서브에이전트/툴 계약을 추가하는 것만으로 루프가 확장**되고, 각 단계 실패를 Orchestrator가 격리·재시도하는 무인 운영이 정적 파이프라인보다 자연스럽기 때문이다. 단 이 이점은 Phase 0 반증선을 통과해야 인정되며, 미검증 시 폴백한다.

## 2. 에이전트 구성

| 에이전트 | 책임 | 입력 | 산출(착지점) |
|---|---|---|---|
| **Orchestrator** | 사이클 계획·서브에이전트 위임·이벤트 기록 | 스케줄 트리거 | `cycle`, `run_event` |
| **Topic** | 개발자 주제 발굴 | `topic_stats`, `playbook`, **`research_trends` 툴 [v2]**([04](04-트렌드조사.md)) | `topic`, `content_item.topic_id` |
| **Content** | 포맷별 대본/카피/문안 + **훅 분리 생성 [v2]**(FR-G5) | 주제, 플레이북 | `content_item.body`, `media_spec` |
| **Media** | 이미지 카드 / 영상 합성(결정론) | `media_spec` | `media_asset`(checksum) |
| **Publisher** | 채널별 발행(멱등) | `content_item`, `channel` | `publication`, `publish_attempt` |
| **Analyst** | 지표 폴링·reward·분석글 | 발행 이력 | `metric_*`, `reward`, `analysis_note` |
| **Growth** | 다음 사이클 변형 선택(결정론) | `topic_stats` | `cycle.decision` |

## 3. 에이전트 코어 요구사항 (FR-C)

| ID | 요구사항 | 수용기준 |
|---|---|---|
| FR-C1 | 코어 = **deepagents 프레임워크를 그대로 도입**. Orchestrator(main) + 서브에이전트(Topic/Content/Media/Publisher/Analyst/Growth) 구성 | deepagents로 한 사이클(기획→제작→발행→학습)이 관통 실행 |
| FR-C2 | 서브에이전트는 **툴 계약**을 통해서만 외부와 상호작용: `research_trends`**[v2]**·`render_media`·`publish`·`poll_metrics`·`read_stats`·`write_playbook` | 각 툴은 타입 시그니처 고정, 에이전트가 임의 부작용 못 냄 |
| FR-C3 | LLM 판단 계층 = Claude(`claude-sonnet-5`) + **[v2] 대량 작업은 Gemini Flash free tier 혼합**. 모델·시계·transport는 **주입식**(테스트에서 가짜 모델 대체 가능) | 가짜 모델로 한 사이클 결정론 재현 테스트 green |
| FR-C4 | LLM 산출 착지점은 **3곳으로 열거**(`content_item.body`·`playbook.guidance`·`analysis_note.body`). 그 외 수치/제어는 코드만 | 착지점 외 LLM 기록 경로 부재 테스트 |
| FR-C5 | 사이클 계획·위임은 Orchestrator가 수행, 각 서브에이전트 호출을 `run_event`로 관측 | 사이클 로그로 에이전트 흐름 재구성 가능 |
