# 03. 딥에이전트·트렌드 조사

> 담당 역할: **역할 B (콘텐츠·에이전트)** · 관련 요구사항: 5, 15, 16, 17 · 상위 문서: [기획서 총괄](../기획서.md)
> 이식 기반: feedr-clone `autopilot-runner`(툴 기반 에이전트) + `research.ts`(무료 트렌드 7소스)

## 1. 에이전트 사이클 (agent-cycle.yml 1회 실행 = 1계정 1사이클)

```
1 research_trends(키워드)        ← 무료 7소스 다이제스트 (§3)
2 pick_topic                     ← 플레이북 + 최근 교훈 + 주제별 과거 성과 참조
                                    hybrid: 3~5개 topic_suggestions 저장 후 종료(사람 선택 대기)
3 write_script                   ← 훅 문장 별도 생성(패턴 5종 중 선택·기록) + 본문 대본
4 build_media_spec               ← 씬 구성·자막·시각 요소를 JSON으로 확정 ([04-영상제작] §3)
5 synthesize_tts → render_video  ← 코드 실행 (LLM 아님)
6 self_review                    ← LLM 검수 + 코드 가드(규격·한도·금지어·직전 N건과 구조 유사도)
7 enqueue_publish                ← auto: queued / hybrid: pending_approval
8 record_run                     ← 보고서·액션·비용 기록 (autopilot_runs)
```

**통제 원칙**: 수치 계산·한도 검증·발행은 전부 코드가 수행. LLM은 주제 선정·대본·검수·분석글에만 관여하고, 기록 가능한 착지점은 5곳으로 제한([02-데이터모델](02-데이터모델.md) §3).

## 2. 자기개선 루프 (요구사항 5·15·16 — awesome-Self-Improving-Agents 기법 적용)

| 기법 | 적용 |
|---|---|
| **Self-Refine** (자체 검수 루프) | 초안 → 검수 프롬프트(지침 위반·사실오류·중복·훅 강도) → 수정 1회 → 코드 가드 통과 시 확정 |
| **Reflexion** (실패의 언어화) | 발행 N건+지표 누적 후, 성과와 행동을 대조해 `record_lesson`으로 교훈 기록 → 다음 실행 프롬프트에 주입 |
| **자동 프롬프트 개선** (OPRO류) | 성과 상위 콘텐츠의 특징(훅 패턴·주제·길이·발행시간)을 **코드가 추출**해 `update_playbook`으로 플레이북 버전업 → 시스템 프롬프트에 주입 |
| **메모리 계층** | 단기 = 당일 실행 기록(`autopilot_runs`), 장기 = 교훈(`agent_experiences`) + 플레이북(`agent_playbooks`, 버전 보존) |

루프 전체: 발행 → 지표 수집([06-지표·인사이트](06-지표-인사이트.md)) → reward 산출 → 교훈·플레이북 갱신 → 다음 사이클의 주제 선정·대본에 반영. **분석이 자동으로 다음 콘텐츠를 바꾸는 것**이 이 시스템의 핵심 차별점이다.

## 3. 무료 트렌드 리서치 (요구사항 17 — feedr-clone `research.ts` 이식)

7개 소스를 병렬 수집해 마크다운 다이제스트로 합친다. 각 소스는 실패/키 없음이면 조용히 빠짐 — 하나 죽어도 리서치는 계속된다. 타임아웃 10초.

| # | 소스 | 방식 | 비용/한도 |
|---|---|---|---|
| 1 | Google Trends 한국 급상승 | RSS 파싱 | 무료, 무인증 |
| 2 | 실시간 검색어 top10 | 공개 JSON (보조 소스, 끊길 수 있음) | 무료 |
| 3 | 네이버 블로그/뉴스 최신글 | 공식 검색 API | 무료 25,000회/일 |
| 4 | 네이버 데이터랩 | 검색량 30일 추이 → 상승/유지/하락 판정 | 무료 1,000회/일 |
| 5 | YouTube 인기영상 | `chart=mostPopular&regionCode=KR` | 1unit (일 10,000) |
| 6 | (선택) 커뮤니티/뉴스 피드 | 개발/IT 도메인 소스로 교체 검토 (GitHub 트렌딩, GeekNews RSS 등) | 무료 |
| 7 | Gemini 웹 리서치 | `google_search` 그라운딩 | 무료 티어 내 |

**할루시네이션 방지 규칙(계승)**: "리서치 결과로 확인 안 되는 내용은 절대 소재로 쓰지 않는다"를 시스템 프롬프트에 고정.

## 4. LLM 혼합 전략 (요구사항 17)

| 작업 | 모델 | 근거 |
|---|---|---|
| 트렌드 다이제스트 요약, 자막 분절, 해시태그, 알림 원인 분석 | Gemini Flash (무료 1,500회/일) | 대량·저난도 |
| 주제 선정, 대본(훅 포함), 자체 검수 | Gemini Flash → 품질 미달 시 Pro | 무료 우선, 필요 시 승격 |
| 주간 인사이트 분석글, 플레이북 갱신 | 상위 모델 (Gemini Pro 또는 Claude — 주 수 회 소량) | 판단 품질이 실험 가치를 좌우 |

**비용 방어(코드 상수)**: 사이클당 LLM 호출 상한(예: 12회) + 일일 비용 상한. 초과 시 사이클 중단 + 알림. 호출마다 추정 비용을 `autopilot_runs.cost_estimate`에 적산 — S4 지표(사이클당 비용)의 원장.

## 5. 에이전트 프레임워크(deepagents 등) 도입 판정 기준

본 설계는 deepagents **프레임워크**를 도입하지 않고 검증된 자체 툴 기반 루프를 쓴다(§1). 근거: 사이클이 고정 8단계 파이프라인이라 동적 계획이 불필요하고, 계획 오버헤드가 비용 절감 원칙과 충돌하며, Python 스택이 이식 자산(TS)과 어긋난다. 단 "이득이 관측되면 도입"을 감이 아니라 아래 규칙으로 판정한다 — **트리거(검토 시작)와 판정(도입 여부)을 분리**하고, 문턱값은 운영 데이터 확인 후 고정한다.

### 5.1 트리거 — 자체 루프의 고통 신호 (기존 수집 데이터로 측정)

| # | 신호 | 측정 방법 | 문턱(초안) |
|---|---|---|---|
| T1 | 오케스트레이션 기인 실패 (API 오류가 아닌 상태 전이·부분 재시도·재개 로직 버그) | `autopilot_runs` 실패 분류 — error_class에 `orchestration` 추가 | 최근 2주 실패 중 ≥30% |
| T2 | 고정 파이프라인 한계 — 사이클 중간 재계획·조건부 단계 삽입 요구 발생 | 백로그 라벨 카운트 | 3건 이상 누적 |
| T3 | 확장 리드타임 증가 — 채널 추가에 provider 파일 1개가 아니라 루프 수정이 필요 | 신규 채널 PR의 루프 코드 diff | 2회 연속 발생 |
| T4 | 루프 코드 비대화 — 사실상 프레임워크 재발명 | 루프+상태관리 코드 라인 수 | 이식 원본(~130줄)의 5배 초과 |
| T5 | 중단/재개 요구 — hybrid 승인 이상의 다단계 사람 개입(중간 검토→재개) | 기능 요구 확정 여부 | 1건 확정 시 |

**트리거 2개 이상 충족 → 도입 검토 스파이크 시작.** 미충족이면 재검토하지 않는다.

### 5.2 판정 — 스파이크 A/B (예상 2~3일, 툴 계약 유지 덕에 저비용)

같은 툴 정의를 deepagents에 등록하고 동일 사이클을 두 방식으로 실행(실 API는 가짜 어댑터)해 비교한다:

| 판정 지표 | 측정 | 도입 조건 |
|---|---|---|
| 결정론·통제 (착지점 제한, 가짜 모델 재현) | 재현 테스트 통과 여부 | **필수 통과 — 미달 시 즉시 탈락** |
| 토큰/비용 | 사이클당 LLM 호출 수·cost_estimate | +30% 이내 (계획 오버헤드 허용 상한) |
| 사이클 완주율 | 동일 조건 N회 실행 | 자체 루프 이상 |
| 트리거였던 고통의 해소 | 해당 실패 시나리오/분기 구현 재현 | 자체 루프 대비 명확히 단순·안정 |
| 구현·유지 비용 | 스파이크 실측 시간, 코드 diff | 이관 비용 < 향후 절감 추정 |

**전 항목 충족 시에만 이관.** 하나라도 미달이면 자체 루프 유지. 판정 결과는 어느 쪽이든 docs/에 기록한다.

> 이 규칙은 기존 팀 문서(PLAN.md §5)의 "멀티에이전트는 목적이 아니라 검증 대상인 수단"이라는 반증선 원칙을 선제 적용한 것이다 — 검증된 루프로 시작하고, 이득이 데이터로 증명될 때만 프레임워크로 이동한다.
