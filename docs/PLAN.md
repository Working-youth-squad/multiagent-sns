## 1. 한 줄 정의

**개발자 주제 콘텐츠**를 **IG 피드 게시물 · IG 릴스 · YouTube 쇼츠**에 **딥에이전트가 자동으로 기획·제작·발행**하고, **반응(지표)을 학습**해 **채널을 키우는** 멀티에이전트 자율 성장 엔진.

## 2. 배경 · 목표

**누구의 어떤 고통인가.** 기술 브랜딩을 원하는 개발자/소규모 팀은 콘텐츠의 가치는 알지만 **꾸준한 발행을 지속하지 못한다.** 주제 발굴 → 대본/카드 제작 → 채널별 규격 맞춤 → 발행 → 반응 분석 → 다음 개선의 루프가 매 사이클 수십 분~수 시간의 반복 노동을 요구하고, 본업(개발)에 밀려 채널이 방치되기 때문이다. 즉 **1회성 제작이 아니라 "지속"이 병목**이다.

**기존 수단 대비 차별점.**

| 대안 | 한계 | 본 프로젝트의 차별 |
|---|---|---|
| 수동 운영 | 지속 불가(본업에 밀림), 분석·학습이 감(感) | 루프 전체 무인 자동화 + 반응 기반 학습 |
| Buffer/Hootsuite 등 예약 발행 툴 | **예약만** 대신, 콘텐츠 제작·주제 선택·개선은 사람 | 제작·선택·개선까지 에이전트가 수행 |
| 단발 생성형 콘텐츠 툴 | 1회성 생성, 반응을 다음 콘텐츠에 되먹이지 않음 | 지표→reward→밴딧으로 **채널이 스스로 학습** |

**전제(수요 가설).** 위는 검증된 시장 데이터가 아니라 **팀의 관찰 기반 가설**이다. 본 라운드의 대상(단일 운영자/팀 자기 채널)에서 M1(§9 Phase 1) 실환경 관통으로 "지속 자동화가 실제로 성장 기울기를 만드는가"를 먼저 자기 검증한 뒤 확장 여부를 판단한다.

**목표.**
- 개발자 브랜딩/채널 성장의 반복 루프(주제 발굴 → 콘텐츠 제작 → 멀티채널 발행 → 반응 수집 → 학습 → 개선)를 **자율 에이전트 루프**로 무인 자동화한다.
- **핵심 성과 지표**: 자기 채널의 시간에 따른 성장(조회수·팔로워·저장·시청유지 등 goal 기준 **기울기**). 타 계정과의 절대 비교는 하지 않는다(과장 방지). 정량 목표·측정 절차는 [`SPEC.md` §5.1 성공지표](SPEC.md) 참조.

## 3. 범위

**포함(이번 라운드)**
- 채널: IG 피드(카드뉴스 이미지) · IG 릴스(영상) · YouTube 쇼츠(영상) — **전부 공식 API**.
- 영상: **템플릿 코드 합성**(자막+슬라이드+TTS, ffmpeg/moviepy). 생성형 비디오 모델 미사용.
- 코어: **deepagents 프레임워크 그대로 도입**(Orchestrator + 서브에이전트).
- 학습: 반응 지표 기반 밴딧(주제×포맷×채널 선택) + 플레이북 갱신 + LLM 분석글(정직 귀인).
- 운영: 상주 러너(스케줄러) + PostgreSQL + Docker Compose + GitHub Actions CI. 웹 대시보드는 선택.
- 대상: **단일 운영자/팀의 자기 채널**.

**미포함(후속)**
- 다중 사용자 SaaS(다중테넌트)·타인 계정 대행 → Meta/Google App Review 게이트 발생, 이번 범위 밖.
- TikTok 등 추가 채널, 생성형 비디오, 실시간 라이브.

## 4. 시스템 아키텍처

전체 그림: [`diagrams/architecture.mermaid`](diagrams/architecture.mermaid)

```
슬롯 스케줄러(러너)
      │ 사이클 트리거
      ▼
Orchestrator (deepagents main)
  ├─ Topic Agent     주제 발굴(트렌드·플레이북 참조)
  ├─ Content Agent   대본/카피/카드 문안 (LLM)
  ├─ Media Agent     이미지 카드 / 영상 템플릿 합성 (결정론 렌더)
  ├─ Publisher Agent IG Graph API · YouTube Data API (멱등 발행)
  ├─ Analyst Agent   지표 폴링 → reward → 분석글(정직 귀인)
  └─ Growth Agent    밴딧: 다음 사이클 변형(주제×포맷×채널×시각) 선택
      │
      ▼
PostgreSQL (단일 DB) ── 웹 대시보드(선택)
```

**제어 채널 분리**: 통제=코드(상태·수치·스케줄) · 판단=LLM(주제/글/분석 서술) · 경계=툴 타입 계약 + DB 착지점(3곳). LLM은 열거된 곳에만 기록하고 수치는 코드가 계산한다.

## 5. 멀티에이전트 구성 (deepagents)

**왜 멀티에이전트(파이프라인이 아니라)인가 — 채택 근거와 반증선.** 본 루프의 6단계는 상당 부분 순차적이며, "단순 함수 파이프라인 + LLM 호출 몇 개"로도 성립할 수 있다. deepagents 멀티에이전트를 택하는 이유는 **(a)** 사이클 계획·서브에이전트 위임을 Orchestrator가 동적으로 조정(실패 채널 격리·재시도·조건부 스킵)하는 제어 흐름이 정적 파이프라인보다 자연스럽고, **(b)** 각 서브에이전트를 툴 계약 seam으로 독립 개발/교체할 수 있기 때문이다. 다만 본 설계는 의도적으로 LLM을 **착지점 3곳**으로 가두므로(§4), 여기서 "멀티에이전트"는 *자율 재량*이 아니라 *책임 분할 + 오케스트레이션*을 뜻한다.

> **반증선(Phase 0 게이트와 연동):** deepagents가 3대 계약(주입·결정론·착지점 통제)을 지원하지 못하거나, 오케스트레이션 이득이 순차 파이프라인 대비 관측되지 않으면 → **자작 오케스트레이터 또는 순수 파이프라인으로 폴백**한다(§9 Phase 0 ①, §10 리스크). 즉 멀티에이전트는 *목적이 아니라 검증 대상인 수단*이다.

| 에이전트 | 책임 | 입력 | 산출(착지점) |
|---|---|---|---|
| **Orchestrator** | 사이클 계획·서브에이전트 위임·이벤트 기록 | 스케줄 트리거 | `cycle`, `run_event` |
| **Topic** | 개발자 주제 발굴 | `topic_stats`, `playbook` | `topic`, `content_item.topic_id` |
| **Content** | 포맷별 대본/카피/문안 작성 | 주제, 플레이북 | `content_item.body`, `media_spec` |
| **Media** | 이미지 카드 / 영상 합성(결정론) | `media_spec` | `media_asset`(checksum) |
| **Publisher** | 채널별 발행(멱등) | `content_item`, `channel` | `publication`, `publish_attempt` |
| **Analyst** | 지표 폴링·reward·분석글 | 발행 이력 | `metric_*`, `reward`, `analysis_note` |
| **Growth** | 밴딧으로 다음 변형 선택(결정론) | `topic_stats` | `cycle.decision` |

발행 사이클: [`diagrams/publish-cycle-sequence.mermaid`](diagrams/publish-cycle-sequence.mermaid)
학습 루프: [`diagrams/learning-loop-sequence.mermaid`](diagrams/learning-loop-sequence.mermaid)

## 7. 개발 원칙 (팀 공통)

1. **공식 API만** — 비공식 스크래핑/자동화 금지(계정 정지 리스크).
2. **결정론 재현** — 모델·시계·transport 주입, 시드 고정. 가짜 모델로 사이클 재현 테스트.
3. **멱등 발행** — 이중 발행 0(상태머신 + 재시작 복구).
4. **missing=NULL** — 지표 결측을 0으로 채우지 않음(DB CHECK 강제).
5. **정직 귀인** — LLM 분석글은 근거 있을 때만 인과 주장, 없으면 "근거 부족". 수치는 코드만.
6. **자기 베이스라인 성장만** — 타 계정 절대 비교 금지, 한계 정직 표기.
7. **시크릿 암호화** — 토큰 평문 저장 금지.
8. **thin spec** — 경계·데이터·측정만 고정, 에이전트 내부 행동은 프롬프트/플레이북에.

## 8. 모듈 · Task 분할 (팀 협업 단위)

각 모듈은 독립 개발 가능하도록 **툴 계약/DB 스키마를 seam**으로 분리했다. 담당자는 협의로 배정.

| # | 모듈 | 산출물 | 의존 | 예상 난이도 |
|---|---|---|---|---|
| **M1** | 인프라·DB | 스키마·마이그레이션, Docker Compose, config, 시크릿 암호화 | — | 중 |
| **M2** | 에이전트 코어 | deepagents Orchestrator+서브에이전트 골격, 툴 계약, LLM 주입, 결정론 하네스 | M1 | 상 |
| **M3** | 콘텐츠 생성 | Topic/Content 에이전트 프롬프트, `media_spec` 스키마 | M2 | 중 |
| **M4** | 미디어 렌더 | Pillow 카드 렌더 + ffmpeg/TTS 영상 합성, 규격 검증 | M1 | 상 |
| **M5** | 발행 어댑터 | IG Graph API + YouTube Data API 클라이언트, 멱등 원장, 오류 분류 | M1 | 상 |
| **M6** | 지표·학습 | 폴러, RewardFn, 밴딧, topic_stats/playbook, 분석글+검증기 | M1, M5 | 상 |
| **M7** | 웹 대시보드(선택) | 온보딩·설정·리포트·알림 | M1, M6 | 중 |
| **M8** | CI/CD·관측 | GitHub Actions, 로깅, run_event 대시 | M1 | 하 |

**병렬화 전략(seam-first)**: 먼저 M1(DB 스키마 + 툴 계약 타입)을 확정해 seam을 고정하면, M3~M6을 가짜(fake) 어댑터/모델로 병렬 개발할 수 있다. 실 API 배선은 각 모듈이 seam 뒤에서 독립적으로.

## 9. 로드맵 (제안)

- **Phase 0 — seam 확정 + 전제 스파이크(게이트)**: M1 스키마 + 툴 타입 계약 + 결정론 하네스. 아래 두 스파이크를 **착수 게이트**로 선행한다.
  - **① deepagents 계약 적합성 스파이크**: deepagents가 본 프로젝트의 3대 계약 — (a) 모델·시계·transport **주입식 대체**, (b) 가짜 모델로 **한 사이클 결정론 재현**, (c) LLM 기록을 **착지점 3곳으로 통제** — 을 실제로 지원하는지 최소 예제로 검증. **게이트 조건**: 세 계약 중 하나라도 프레임워크가 막으면 → deepagents 코어를 버리고 **자작 오케스트레이터로 폴백**(툴 계약·착지점·결정론 하네스는 그대로 유지). 결과를 `SPEC.md` §6 미결정에 기록.
  - **② 콘텐츠 품질 하한 스파이크**: 템플릿 합성으로 만든 릴스/쇼츠·카드 샘플 각 소수를 사람이 검수해 "발행 가능 하한"을 정성 확인. 통과 못 하면 Phase 1 발행 전 **품질 게이트(FR-Q)** 를 필수로 승격.
- **Phase 1 — M1(실환경 관통)**: IG 피드/릴스 + YT 쇼츠 각 1건 자동 발행 → 지표 → reward → 리포트까지 한 번 관통(수동 트리거 허용). **발행 전 품질 게이트(FR-Q) 통과 필수.** **비용 하드 상한(최소 방어선)을 Phase 1부터 적용**: 사이클당 LLM/TTS 호출 상한을 코드 상수로 두고 초과 시 발행 스킵+알림(Phase 2의 학습형 cost cap 이전에 폭주만 막는 최소 가드, `SPEC.md` FR-P6). 초기값은 안전값으로 두고 실측 후 조정.
- **Phase 2 — 자율 루프**: 스케줄러 상주 + 밴딧 학습 + 플레이북 반영 + 분석글. **비용 상한(cost cap)을 Phase 1의 최소 가드에서 학습형(사이클/일 단위 예산·초과 시 탐색 축소)으로 승격**(콜드스타트 탐색기 호출 폭증 방지).
- **Phase 3 — 운영 성숙**: 대시보드, 알림, 비용/한도 관리, 계정 안전 운영.
- **Phase 4(후속)**: 채널 확장·다중 계정 등 범위 확대 검토. **선결: Phase 1~2의 성장 기울기 검증(§2 수요 가설 확인).**

**기간 추정(러프 · 팀 규모/가용시간에 따라 변동).** 아래는 캘린더 계획 수립용 초안이며 확정 일정이 아니다.

| Phase | 개발 기간(추정) | 관측 대기(캘린더) | 비고 |
|---|---|---|---|
| Phase 0 (게이트) | 1~2주 | — | deepagents 계약 + 품질 스파이크 병렬 |
| Phase 1 (관통) | 2~3주 | 발행 후 지표 누적 **수일~2주** | 개발과 관측이 겹침 |
| Phase 2 (자율 루프) | 2~3주 | S1 판정까지 **누적 N사이클 = 수주~수개월** | 성장 기울기는 캘린더 시간이 필요, 개발로 단축 불가 |
| Phase 3 (성숙) | 상시 | — | 운영 |

> **핵심 제약:** S1(성장 기울기)은 **발행→반응 누적**이라는 캘린더 시간을 요구하므로, 짧은 데드라인(예: 해커톤/단기 데모)에는 Phase 2 성과 판정이 물리적으로 불가하다. 단기 목표라면 DoD를 [`SPEC.md` §5-(1~4)](SPEC.md) **엔지니어링 관통**까지로 두고, §5.1 제품 성공은 후속 관측으로 분리한다.
