## 1. 계약

### 1.1 파이썬 (권장)

```python
from sns.research import rank_keywords

ranking = rank_keywords("개발자")

for i, c in enumerate(ranking.candidates, 1):
    print(i, c.text, c.present_count, c.observed_mean, c.rank_std)
```

| 반환 필드 | 뜻 |
|---|---|
| `query` | 사용자가 넣은 질의어 |
| `filter_mode` | `"active"` / `"passthrough"` / `"off"` — §2.2 |
| `band` | 실제 적용된 rank_std 경계. `active`일 때만 값이 있다 |
| `reason` | 사람이 읽는 판정 사유. 그대로 LLM 프롬프트에 넣어도 된다 |
| `sources_ok` / `sources_failed` | 소스별 성패 — 일부 실패해도 나머지로 완주한다 |
| `candidates` | **최종 목록**. 밴드 통과 + 정렬 + `top` 컷 |
| `pool` | 컷 이전 전량 |
| `below_min_present` | ③ 교차검증 하한에 걸려 빠진 것 |
| `dropped` | 밴드 밖으로 잘린 것 |
| `unscored` | rank_std를 잴 수 없어 **판정하지 않은** 후보 — `candidates`의 **부분집합** |
| `excluded` | `(원문, 걸린 제외 키워드)` — `exclude`를 준 경우만 |

`KeywordStat`:

| 필드 | 뜻 | 방향 |
|---|---|---|
| `text` | 키워드 표시 문자열(관측된 첫 표기) | — |
| `variants` | 관측된 **모든 표기 변종**(등장 순) | 제외 판정이 이 전부를 본다 |
| `present_count` | 몇 개 소스가 이 키워드를 내놨나 | **정렬 1순위**. 높을수록 교차검증됨 |
| `observed_mean` | **관측된 소스에서만** 낸 평균 등수 | **정렬 2순위**. 낮을수록 인기 |
| `rank_std` | **관측된 소스들 사이의** 등수 불일치 | `None` = 관측 1건이라 **정의 불가** |
| `per_source` | 소스별 `(pct_rank, present)` | 근거 원자료 |

> **`None`을 0으로 채우지 말 것.** `rank_std=None`은 "불일치가 없다"가 아니라 "불일치를
> 잴 수 없다"(그 후보를 본 소스가 하나뿐)이다. 뭉개면 근거 없는 후보가 근거 있어 보인다.

### 1.2 CLI (다른 프로세스·다른 언어)

```bash
uv run python scripts/rank_keywords.py 개발자 --json
```

`--json`은 `ranking_to_dict()`를 그대로 찍는다 — 파이썬 호출 결과와 모양이 같다.
종료 코드: `0` 정상(후보 0건 포함) / `1` 전 소스 실패 / `2` 인자 사용 오류(빈 질의어 포함).

JSON 최상위 키와 파이썬 필드는 1:1이다. 후보 항목(`candidates`·`pool`·`dropped`·
`below_min_present`의 원소)은 이 모양이다:

```json
{
  "text": "등산화",
  "variants": ["등산화"],
  "present_count": 3,
  "observed_mean": 0.3,
  "rank_std": 0.141421,
  "scored": true,
  "per_source": {"naver_autocomplete": {"pct_rank": 0.25, "present": true}}
}
```

**세지 말고 표식을 읽을 것.** `unscored`는 이름 목록이고 `candidates`의 부분집합이라,
`len(candidates) + len(unscored)`처럼 더하면 실제 후보 수를 넘는다. 항목 단위로 알고
싶으면 `"scored": false`를 본다 — 같은 사실이다.

**`top` 컷으로 잘린 후보는 `pool`에 있다.** `candidates`만 보면 무엇이 잘렸는지 알 수
없다. `below_min_present`는 교차검증 하한(③)에 걸린 것으로, 밴드 밖(`dropped`)과 사유가
다르다.

## 2. 토글 5종

| # | 토글 | 파이썬 | CLI | 기본값 |
|---|---|---|---|---|
| ① | 소스별 | `sources=("google_suggest",)` | `--source` (반복) | 주입된 서비스의 소스 전부 |
| ② | 밴드 on/off · 경계값 | `band=False` · `percentiles=(10,90)` | `--no-band` · `--band 10 90` | on · `(25, 75)` |
| ③ | 교차검증 하한 | `min_present=2` | `--min-present 2` | `1`(제한 없음) |
| ④ | 제외 키워드 | `exclude=[...]` | `--exclude` (반복) | **없음** |
| ⑤ | 제외 매칭 폭 | `exclude_ignore_spaces=True` | `--exclude-ignore-spaces` | `False` |

> ①의 기본값이 "자동완성 3종"이 아니라 "주입된 서비스의 소스 전부"인 이유: `service=`로
> 임의의 소스 레지스트리를 넣을 수 있어야 한다. 기본 서비스(`keyword_service`)를 쓰면
> 결과적으로 자동완성 3종이다.

### 2.1 ④가 기본으로 비어 있는 이유 · ⑤를 켤 때

이 모듈은 **관련성을 판정하지 않는다**(§4). 무엇이 부적절한지는 도메인이 정하는 문제라,
질의어에서 부정 프롬프트를 파생시키는 쪽이 그 목록을 주입한다.

기본 매칭 규율은 공백의 **양**은 무시하되 **존재**는 존중한다 — `"리콜  대상"`은 걸리고
`"최고 장점"`은 걸리지 않는다(공백을 지우면 '고장'이 생겨 오탐).

판정 대상은 **그 후보가 소스들에서 실제로 관측된 표기 전부**(`KeywordStat.variants`)다.
공백만 다른 표기는 한 후보로 병합되는데, 병합 뒤 대표 표기 하나만 보면 어느 소스가 먼저
나열되느냐에 따라 제외 여부가 뒤집힌다. 변종을 전부 훑어 그 순서 의존을 없앴다.

**남는 한 가지 경우가 ⑤다.** 어느 소스도 띄어쓴 형태를 내지 않았는데 `exclude`에는
띄어쓴 형태만 있으면(소스가 `"리콜대상"`만 주고 목록엔 `"리콜 대상"`만 있는 경우) 변종
탐색으로도 안 잡힌다. 한국어에는 단어 경계가 없어 공백 무시 부분일치는 오탐과의 맞바꿈이다:

```python
rank_keywords("기아", exclude=["리콜 대상"])                              # "리콜대상" 통과
rank_keywords("기아", exclude=["리콜 대상"], exclude_ignore_spaces=True)  # "리콜대상" 차단
rank_keywords("등산", exclude=["고장"], exclude_ignore_spaces=True)       # "최고 장점"도 차단 ← 오탐
```

**부정 키워드를 좁게 통제할 수 있을 때만 켠다.** 브랜드 리스크 단어처럼 짧고 흔한 음절
조합이 아닌 목록이면 켜는 쪽이 안전하고, 일반어가 섞인 목록이면 끄고 ④에 띄어쓰기 변종을
함께 넣는 편이 낫다.

### 2.2 `filter_mode` 3값을 구분해서 쓸 것

| 값 | 뜻 | 챗봇이 사용자에게 할 말 |
|---|---|---|
| `active` | 밴드를 실제로 적용했다 | "3소스 교차 분석으로 걸렀습니다" |
| `passthrough` | 켰지만 표본 부족 | "데이터가 적어 필터 없이 전부 보여드립니다" |
| `off` | 호출자가 껐다 | "전체 목록입니다" |

`passthrough` 조건은 둘: 참여 소스 < 2, 또는 **rank_std가 정의된 후보** < 4.
후자가 실전에서 자주 걸린다 — 자동완성이 서로 잘 겹치지 않는 질의어에서는 정의된 후보가
2개뿐이라 필터를 열 수 없고, 모듈이 그 사실을 `reason`에 그대로 적는다.

> **`active`여도 미판정 후보가 섞여 있다.** `unscored`는 판정을 받지 않고 통과한 것이다.
> "걸렀다"고 말할 수 있는 대상은 `dropped`가 실제로 생긴 경우뿐이다.

## 3. 계산 방식

```
소스별 순서열                    백분위 등수(등수 ÷ (길이+1))
naver:   [연봉, 로드맵, 되는법]    연봉 .25  로드맵 .50  되는법 .75
google:  [연봉, 되는법, 노트북]    연봉 .25  되는법 .50  노트북 .75
youtube: [연봉, 짤,     되는법]    연봉 .25  짤    .50  되는법 .75
                                  ↓ 없는 소스는 등수만 1.0으로 채우고 분산에는 넣지 않는다
키워드     naver  google  yt    소스  obs_mean  rank_std
연봉        .25    .25    .25    3     .250      .0000   ← 3소스 합의
되는법      .75    .50    .75    3     .667      .1179
로드맵      .50     —      —     1     .500       None   ← 관측 1건: 정의 불가
짤           —      —     .50    1     .500       None
노트북       —     .75     —     1     .750       None
```

네 가지가 코드에 박혀 있다.

1. **소스 원값은 흐르지 않는다.** 데이터랩 ratio·조회수는 단위가 달라 합치면 단위 차이만
   측정한다. 입력이 문자열 순서열뿐이라 값을 넣을 자리 자체가 없다.
2. **분모가 길이+1이다.** "결측 = 최하위+1"을 리스트 길이로 나누면 `(L+1)/L > 1.0`이 되어
   등수가 1을 넘는다. +1 분모는 결측을 정확히 1.0으로 보내고 관측 항목은 전부 그 아래에 둔다.
3. **분산은 관측된 등수끼리만. 관측 1건이면 `None`.** 결측 1.0은 관측값이 아니라 대입값이다.
   분산에 넣으면 분산이 "불일치"가 아니라 "결측이 몇 개인가"를 잰다.
4. **정렬을 대입 상수에 맡기지 않는다.** 결측을 1.0으로 대입한 평균으로 정렬하면 그 상수가
   "몇 소스가 봤나"와 "얼마나 높았나"의 교환비를 혼자 정한다. 1.0에 근거가 없다.

3·4는 관념이 아니라 실측에서 나왔다. 대입값을 분산에 넣던 판에서는 **2개 소스가 아는
키워드와 한 소스만 아는 밈 문구가 같은 표준편차**를 받았고, 단일 소스 구간에서
`rank_std = √2 × (1 − 평균등수)`가 되어 평균 등수와 상관계수 −1, 즉 새 정보가 0이었다.

**실패 소스와 빈 관측은 다르게 다룬다.** 장애 소스(`ok=False`)는 통계에서 아예 빠진다 —
결측으로 채우면 통계가 장애의 함수가 되어 소스 격리(FR-G4)의 취지가 무너진다. 성공했지만
항목 0개인 소스는 "관측했고 없었다"이므로 참여시킨다.

## 4. 이 모듈이 하지 않는 것 — 관련성 판정

등수 분산만 보므로 **밈·오타도 통과한다.** 예를 들어 `"개발자"`를 넣으면 유튜브 자동완성이
주는 `"개발자 집주소 삽니다"` 같은 밈 문구가 목록에 남는다. 다만 그 후보는 `rank_std=None`
(교차 소스 근거 0)으로 표시되고 교차검증된 후보 **아래**에 놓인다 — 통계가 말할 수 있는
정직한 위치는 거기까지다.

목록에서 **빼는** 것은 도메인 판정이고, 이 자리는 두 가지가 채운다:

1. **`exclude=` 주입** (토글 ④) — 질의어에서 파생시킨 부정 프롬프트 목록
2. **뒤쪽 LLM 층** — 후보 목록을 받아 소재 적합성으로 고르는 단계

## 5. 알아둘 것

- **질의어 구체성이 결과 품질을 지배한다.** `"개발자"`는 중의적이라(네이버가 안드로이드
  `개발자옵션` 계열로 해석) 소스들이 서로 다른 이야기를 해 교차 후보가 2개뿐이다. 반면
  `"등산"`은 `등산화`·`등산복`이 3소스 공통으로 잡혀 밴드가 정상적으로 열린다.
  챗봇이 `filter_mode`와 `unscored` 비율을 보고 "키워드를 더 구체적으로" 안내할 수 있다.
- **소스당 항목은 9~10개다.** `--limit`을 더 줘도 자동완성 엔드포인트가 그 이상 주지 않는다.
- **UA를 반드시 단다.** 없으면 구글 자동완성이 EUC-KR로 응답해 파싱이 죽는다(회귀 테스트로
  고정). 서비스가 소스를 격리하므로 이 결함은 조용히 "소스 실패"로만 보인다.
- **DB 저장은 넣지 않았다.** 챗봇 1회 응답은 순수 계산이면 충분하고, 영속이 필요해지면
  PG 마이그레이션이 따라와야 하는 별도 결정이다.
- **미수정 리뷰 지적 8건이 있다** — [리뷰 문서](../review/2026-08-25-pr37-keyword-ranking-review.md).
  머지 후 후속 브랜치에서 일괄 수정한다. 그 전까지 **연동에 직접 걸리는 것은 둘**이다:
  - **R2** — `exclude`(§2 토글 ④)가 공백 변종을 놓친다. `"리콜 대상"`을 넣어도 `"리콜대상"`은
    통과할 수 있다. 당분간 **띄어쓰기 변종을 함께 넣을 것**.
  - **R7** — `ranking_to_dict`(§1.2 JSON)에 `pool`이 없고, `unscored` 항목은 `candidates`에도
    들어 있다. `candidates + dropped + unscored`로 총계를 세면 **중복 집계된다**.
